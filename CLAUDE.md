# CLAUDE.md

Guidance for Claude Code in this repository.

## Project

gearmulator-md-drums is the Elektron Machinedrum's synthesis engines as a plug-in built like The Usual Suspects' Gearmulator plug-ins (**TUS**: Osirus, OsTIrus, Vavra, Xenia, Nodal Red 2x, JE-8086) and edited like **Overbridge**. One window edits the machine tab by tab: each track's machine, synthesis, effects, routing and LFO, the master effects, the mix, the Kit. Every parameter is a host parameter that Live can automate, and Live's clips sequence the 16 tracks. The real firmware ROM runs on the emulated UC (ColdFire, `source/mc68k/`) and two DSP56300s (`source/dsp56300/`); the firmware's own sequencer stays idle.

The TUS architecture, with OsTIrus as the reference (`osTIrusJucePlugin/` over `virusJucePlugin/`, in the tree but not built): a thin plug-in over the emulated machine, its parameters and their MIDI messages declared in the JSON (`midipackets`, `regions`), presets in the Patch Manager (`virusJucePlugin/PatchManager.*`), a skin whose controls bind to parameters. The MD plug-in inherited from md-mm does it its own way: CC mapping in C++ (`mdLib/mdautomation.*`), an editor generated by a script, BIBLIO in place of the Patch Manager.

**Latency** is a requirement, measured rather than assumed: the time from a host note to the sound at the plug-in's output, and its jitter. A change to the trig path or the render pipeline reports both, before and after.

The plug-in drives the intact firmware over MIDI: notes trigger tracks, host parameters reach it as CC, Kits travel as SysEx, and the editor is a layer over those protocols. Engines without the UC were ruled out in `.scratch/parallel-transport/issues/07-go-no-go.md` on CPU and effort: the sequencer costs about 6 points of UC, dropping the UC leaves DSP1 (the busiest core) as heavy, and the DSPs' HI08 protocol would need reverse engineering machine by machine. **Decided otherwise on 2026-10-06: the plug-in moves to the engines without the OS.** The protocol is now documented in public (`.scratch/uc-less-engines/`), and Machinemodule's engine (sd88me, AGPL-3.0), imported as `source/elektron/md/mdEngine/`, runs OS 1.63's engines without it: DSP2 emulated, the OS's own machine, LFO and smoothing routines called in a 68k emulator, DSP1's track chain and mix in C++. Measured against the full firmware: the same samples (`mdEngineFirmwareTest`), about a tenth of the CPU, 0.48 ms of note-to-sound latency against ~5.4 ms, and no 14 s silent boot. The combined work is AGPL v3 (`NOTICE.md`). Master effects come later; the plug-in still runs the full firmware until the engine is wired in.

The repository split on 2026-10-06 from [c0remusic/gearmulator-md-mm](https://github.com/c0remusic/gearmulator-md-mm), which keeps the full-machine plug-ins (sequencer editor, BIBLIO's patterns, pattern chains). The Monomachine is out of this project: its plug-in, tests and code paths may go, and nothing here maintains them. The other Gearmulator synths stay out of the build.

## State on 2026-10-06

- **Sound:** 26 host parameters per track, 16 tracks (`mdJucePlugin/parameterDescriptions_md.json`), sent as CC (`mdLib/mdautomation.*`). The parameter pages are part of the JUCE parameter IDs that Live sets store: append pages, keep existing numbers.
- **Trigs:** every host note reaches the firmware's MIDI input (`Hardware::pumpScheduledMidi` in `mdLib/mdhardware.cpp`); the front panel plays no part. On the base channel, notes 36 38 40 41 43 45 47 48 50 52 53 55 57 59 60 62 (white keys C2–D4) trigger tracks 1–16, and velocity scales the level. Notes stay silent until ~14.3 s of audio after boot although `isFirmwareMidiReady()` holds at 2.3 s: the firmware reads MIDI from 3 s but drops it through its own boot (`mdTrigLatencyFirmwareTest --startup`). Open: a note ≥ 64 seemed to start a pattern.
- **Latency:** the plug-in reports 2 blocks by default (`DefaultLatencyBlocks` in `mdJucePlugin/mdPluginProcessor.h`), so that the machine renders ahead on its own threads (`md::AsyncRender`). The firmware adds 3.4–4.0 ms beyond that at least, about 5.4 ms on average, with about 3 ms of jitter, at every latency setting (`mdTrigLatencyFirmwareTest`, by hand; numbers in `.scratch/parallel-transport/implementation-log.md`).
- **Machines:** `$5B` ASSIGN MACHINE (`automation::sysex::assignMachine` in `mdLib/mdsysexautomation.*`, table in `mdLib/mdmachines.*`) runs from the editor's machine picker only; no host parameter selects a track's machine yet.
- **Editor:** the top bar has JOUER, SON, MIX, BIBLIO and SYSTÈME. SON, MIX, the master effects and BIBLIO's Kits are the material for the tabs; JOUER (steps, chains) and BIBLIO's patterns serve the internal sequencer. Skins are generated: edit `.scratch/md-editor/tools/gen_editor.py` and regenerate as `.scratch/md-editor/README.md` says. That README also holds the SysEx formats found and the facts verified on firmware.
- **Plug-in identity:** `mdJucePlugin` (the full firmware) is still md-mm's: "Gearmulator MD", code `Tmdr` (`mdJucePlugin/CMakeLists.txt:95`). `C:\Program Files\Common Files\VST3\Gearmulator MD.vst3` is a symlink to md-mm's `editor-test` worktree build, which the user plays in Live: never install `mdJucePlugin` from here. The engine plug-in has its own: "MD Drums", manufacturer `C0rm`, code `Mddr` (`mdDrumsPlugin/`).
- **MD Drums** (2026-10-06, `mdDrumsPlugin/` over `mdDrums/`): the engines without the OS as a VST3 with JUCE's generic editor. Notes 36–51 on any channel trigger tracks 1–16 with velocity; per track, the machine (by id), the 24 parameters, level and mute are host parameters (`t<n>_<name>` IDs: keep them). SYN1-8 show their name on the track's machine ("PTCH 64"). Outputs: the dry main mix (no master effects), plus 16 optional mono outputs "Track 1"–"Track 16" (after the track's effects and VOL, before PAN); enabling one takes its track out of the main mix. Everything is resampled (Lagrange) when the host is not at 44.1 kHz. It finds `elektron_sps1-1uw_os1.63.bin` as `mdDrums::Engine::findFlashImage` says. The ROM machines play the UW sample bank in that image (ROM-01 to -32 in the factory bank; ROM-33 to -48 empty and silent), which `md::fw::loadRomBankFromFlash` turns into the voice DSP's directory and 12-bit data as OS 1.63's boot does (`$20d20e`); the format is in `mdEngine/tools/mdfw/Firmware.h`. RAM machines (RAM-R/P) do not play.

## Where things are

- `source/elektron/md/mdDrums/`: `mdDrums::Engine`, mdEngine as the plug-in drives it (flash lookup, defaults, 32-sample block rendering), without JUCE. `mdDrumsPlugin/`: the JUCE processor over it.
- `source/elektron/md/mdEngine/`: the engines without the OS (`EngineT` in `engine/MdEngine.h`), with its origin and local changes in `README.md`. Musashi's entry points serve one CPU class per executable, so nothing links it with `mdLib`'s `Microcontroller`: tests that compare the two run in separate processes.
- `source/elektron/md/mdLib/`: the machine. `mdhardware.*` runs the UC and the DSPs and delivers MIDI and panel events; `mddevice.*` is the `synthLib::Device`; `mdautomation.*` maps host parameters to CC; `mdsysexautomation.*` holds the SysEx codecs (Kits, patterns, `$5B`, master effects).
- `source/elektron/md/mdJucePlugin/`: the plug-in. `mdPluginProcessor.*`, `mdController.*` (parameters and SysEx traffic), `mdEditor.*` and its views, `parameterDescriptions_md.json`, skins in `skins/mdDefault/`.
- Tests: firmware and protocol tests in `mdLibTest/`, plug-in tests as `mdJucePlugin/*Test.cpp`.
- Shared Gearmulator layers: `synthLib/` (Device, MIDI), `jucePluginLib/` (parameters, MIDI Learn, Patch Manager), `jucePluginEditorLib/`, `juceRmlUi/` (RmlUi inside JUCE).

## Build

Windows, Visual Studio 2022, build directory `temp/cmake_vs22`, Elektron synths and VST3 only:

```powershell
cmake . -B temp/cmake_vs22 -G "Visual Studio 17 2022" -DBUILD_TESTING=ON `
  -Dgearmulator_SYNTH_OSIRUS=OFF -Dgearmulator_SYNTH_OSTIRUS=OFF -Dgearmulator_SYNTH_VAVRA=OFF `
  -Dgearmulator_SYNTH_XENIA=OFF -Dgearmulator_SYNTH_NODALRED2X=OFF -Dgearmulator_SYNTH_JE8086=OFF `
  -Dgearmulator_BUILD_JUCEPLUGIN_AU=OFF -Dgearmulator_BUILD_JUCEPLUGIN_CLAP=OFF -Dgearmulator_BUILD_JUCEPLUGIN_LV2=OFF `
  -Dgearmulator_BUILD_JUCEPLUGIN_Standalone=OFF -Dgearmulator_BUILD_JUCEPLUGIN_VST2=OFF -Dgearmulator_BUILD_FX_PLUGIN=OFF
cmake --build temp/cmake_vs22 --config Release -j 6 --target mdJucePlugin_VST3
```

- `jucePluginLib/pluginVersion.cpp` recompiles on every build (version timestamp, MSB8065 by design): a build with no change still compiles one file.
- Run firmware executables by hand only under a wall-clock guard (`Start-Process -PassThru` + `WaitForExit(ms)`, kill on timeout).
- Worktrees (`.claude/worktrees/*`) start without submodules or build directory. Check the submodules out from this checkout's module repositories, offline, then configure a fresh `temp/cmake_vs22`:

## Gate

Before every commit and push; ctest only after the build exits 0:

```powershell
$rom = "$env:LOCALAPPDATA\Programs\Gearmulator-Elektron"
$env:GEARMULATOR_MD_FIRMWARE_BIN = "$rom\elektron_sps1-1uw_os1.63.bin"
$env:GEARMULATOR_MM_FIRMWARE_BIN = "$rom\elektron_sfx6-60_os1.32b.bin"
$env:MD_AUTOMATION_REQUIRE_FIRMWARE = "1"
cmake --build temp\cmake_vs22 --config Release -j 6 --target mdAudioFirmwareTest mdMidiTimingTest mdHostRxTimingTest mdHostRxFirmwareTest mdAudioQueueTest mdAutomationMidiTest mdAutomationParameterTest mdAutomationFirmwareTest mdParallelTransportFirmwareTest mdTrigLatencyFirmwareTest mdEngineFirmwareTest mdDrumsEngineTest mdDrumsProcessorTest
Copy-Item "$rom\*.bin" temp\cmake_vs22\source\elektron\md\mdJucePlugin\Release
cd temp\cmake_vs22
ctest -C Release -R "^(mdAudioFirmwareTest|mdMidiTimingTest|mdMidiTimingFirmwareTest|mdHostRxTimingTest|mdHostRxFirmwareTest|mdAudioQueueTest|mdAutomationMidiTest|mdAutomationParameterTest|mdAutomationFirmwareTest|mdParallelTransportFirmwareTest|mdEngineFirmwareTest|mdDrumsEngineTest|mdDrumsProcessorTest)$"
```

Green is 22 passed out of 22 in 150 to 230 s: ctest adds the 9 fixture tests these require (`mdEngineFirmwareHits` and `mdEngineFirmwareRomBank` boot the firmware to record the hits and the voice DSP's UW bank that `mdEngineFirmwareTest` compares the engine with).

Both ROMs are required. A firmware test exits 77 without its ROM and ctest reports it Skipped, which proves nothing:
- Most firmware tests read the two variables; the timing tests check the Monomachine as well.
- The tests built on the plug-in processor (`Harness` in `mdJucePlugin/mdAutomationTestSupport.h`) find the ROM as the plug-in does, next to their executable or in its data folder. Only a test that adds the variable's folder to `synthLib::RomLoader` itself sees the variable (`mdParallelTransportFirmwareTest` does, `mdAutomationFirmwareTest` does not): hence the `Copy-Item`. `MD_AUTOMATION_REQUIRE_FIRMWARE=1` makes the Harness tests fail instead of skipping when the ROM is missing.

Known failures outside the gate, on this PC: `mdHostSyncPluginTest` ("MD startup: no result within 60 s of audio": the user's factory cache is rejected) and `mdUwFirmwareTest` (passes about one run in three, 4x cost bound). Compare with these before bisecting.

## Tests

- A test that creates a processor uses `AudioPluginAudioProcessor(model, AudioPluginAudioProcessor::EphemeralConfig{}, false)`: the default constructor starts the MCP server, and Windows shows the user a firewall prompt for every new executable.
- A harness that paces a fake audio callback spin-waits to each deadline: a process without a visible window runs on the 15.6 ms timer, and a sleeping audio thread invents dropouts.
- A new test's `main` sets `setvbuf(stdout, nullptr, _IONBF, 0)`: `_IOLBF` crashes the Microsoft runtime at startup (0xc0000409).

## Critical implementation details

- **State:** `Device::getState()` appends to `_state` with `insert()`, never `assign()`: the Plugin layer has already written its version header there.
- **Device lock:** the editor reads the machine through `mdJucePlugin/mdLiveDevice.*`. `Plugin::withDeviceLocked` pauses rendering, which the host shows as a CPU spike when it runs on every frame or click.
- **Threads:** RmlUi DOM changes happen on the JUCE message thread. From audio or MIDI callbacks, post with `juce::MessageManager::callAsync`, the lambda guarded by the static instance-set pattern against use-after-free.
- **Animation:** the software renderer ignores RmlUi transforms (`RendererJuce::SetTransform` stores the matrix, nothing reads it). Draw what moves with `juceRmlUi::ElemCanvas` (see `mdOutputMetersView.cpp`, `mdCurveView.cpp`), and hide elements with `display`, never a zero scale.
- **Environment overrides** (`MD_*`, `MDMM_*`) go through `mdLib/mdenv.h` (`envOverride`, `envNumber`, `envCount<T>`), where unset, empty and unparsable all count as unset: PowerShell's `SetEnvironmentVariable($n, $null)` leaves an empty variable that child processes see.

## Code conventions

- Tabs (size 4), 120 columns, braces on their own line, namespace content indented; `.clang-format` in `source/`.
- PascalCase classes; camelCase functions, variables and namespaces; `m_` members, `_` parameters (`void func(int _param)`).
- Early returns over nesting. C++17.
- Commit subjects are imperative sentences that say what the change does for the machine ("Write a step edit into the pattern edited, not into A01"); the body says why, with the numbers measured.

## Git

- `origin` is c0remusic/gearmulator-md-drums, default branch `main`. `md-mm` is c0remusic/gearmulator-md-mm: bring its fixes in by cherry-pick or by merging `md-mm/release/md-mm-alpha`, then gate the merged tree.
- Commit messages carry no `Co-authored-by` trailer.
- Stage with explicit pathspecs.
- `source/dsp56300` pins commits of c0remusic/dsp56300-md-mm, the user's fork: changes there are fine.
- CI is md-mm's: `.github/workflows/elektron-*.yml` build MD and MM on pushes to `main` that touch build paths, `mdmm-*.yml` run on pull requests.
